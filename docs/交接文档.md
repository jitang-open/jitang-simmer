### 3.3 核心设计决策

1. **点阵图分档算法**：v0.6.7 起，每张点阵图按自身有效正值的 P95 独立建立比例色阶，再将 P95 等分为 8 个阈值（空白 + 9 档绿色）；总览自然使用较大的总时长尺度，单软件使用各自较小的尺度。v0.8.2 起软件时长再以 5 小时、Token 以 1 亿 Tokens 作为业务硬上限；超出统一顶格，Tooltip 始终显示真实值。
2. **假数据的真实性**：模拟了周末/工作日差异、季节波动、偶发"爆肝日"、设备"未开机日"（约 9%），使点阵图呈现真实的使用节律；固定随机种子 `20260820` 保证每次打开数据一致。
3. **白名单即过滤器**：白名单状态存入全局 `state.whitelist`，所有统计查询函数接收软件 id 列表实时过滤，关闭开关即刻从全部统计中剔除。
4. **多设备聚合规则**：时长类指标多设备**求和**，百分比类指标（CPU/内存/温度等）多设备**取平均**，功耗多设备求和。
5. **Token 解析隔离**：`simmer-token-scan.exe` 固定依赖 `tokscale-core` 提交 `b069c85d...`，只读取 Codex/ZCode/DSH/WorkBuddy 本地日志或数据库并向 C# 采集器输出数字事件；它不读取服务器 Token、不联网。sidecar 超时或损坏只会改变来源状态，不影响软件时长采集。
6. **请求级幂等与隐私**：Token 服务端主键为 `(device_id, source, source_event_id)`；稳定 ID 是上游去重键的 SHA-256。后端不存会话 ID、项目路径、程序路径、提示词、回复、代码、认证信息或原始 usage JSON。
7. **Token 分类互斥**：输入、普通输出、缓存读取、缓存写入、推理五个桶互不重叠，`totalTokens` 必须严格等于五项之和；ZCode、DSH 和 WorkBuddy 中包含缓存/推理的原始字段由固定解析器先消除重叠。
8. **统一选择与按需趋势**：网页设备、年份、Token 来源/provider/model、进程及软件类型共用同一套自定义下拉视觉；Token 时间按钮与顶栏双向同步。总时长和 Token 趋势默认不占用纵向空间，用户点击后再以真实容器宽度重绘。
9. **累计历史与当前来源解耦**：`ai_token_events` 没有 TTL 或自动删除路径；本地日志、应用或扫描目录消失只更新当前来源状态，不删除已上传事件。累计总数/请求数/排行读取全部 SQLite 历史；累计趋势仍以最近 12 个月为展示窗口。若本地来源不可用但服务器已有事件，API 派生为 `history_only / server_history_only`，页面显示“历史已保存”。
10. **硬件采集隔离与语义**：固定使用官方 `LibreHardwareMonitorLib 0.9.6`（MPL-2.0），按传感器类型、硬件类型和名称优先级映射，不依赖单一厂商名称。硬件使用独立一分钟定时器、`hardware-queue.json` 与上报接口；字段允许为 `null`。同设备同分钟幂等合并；“全部设备”功耗求和，其余指标平均。当前值十分钟无更新即失效，0°C 视作驱动的“无读数”并迁移为 `NULL`。

## 四、当前真实链路与后续扩展

1. **当前采集链路**：每台 Windows 设备通过 `GetForegroundWindow` 每 2 秒采样软件，并由 LibreHardwareMonitor 每分钟独立采样硬件；两者分别写本地原子队列，断网保留、恢复后重试。键鼠空闲或锁屏不计软件时长；硬件监控可在托盘设置中独立关闭。
2. **当前接口约定**：Node 后端提供软件年度/趋势/排行、Token 汇总与 `/api/hardware/current`、`/api/hardware/series`，并提供 `GET/PUT /api/settings`。前端连接失败时自动切换 MockDB。
3. **当前聚合规则**：每台设备携带稳定 `deviceId` 上报，服务端按设备和分钟存储；“全部设备”视图由后端查询层聚合。上传接口需要 Bearer Token，重复分钟通过 SQLite 主键幂等去重。
4. **白名单持久化**：v0.6.6 起 SQLite 是白名单与软件元数据的唯一数据源，所有浏览器及 `localhost` / `127.0.0.1` 共享；localStorage 四个旧键继续作为离线缓存与首次迁移来源。后端尚无设置时，仅迁移有实际内容的本地配置，空白新浏览器不会覆盖旧浏览器配置（SRV-05 已完成）。
5. **Token 当前链路**：来源发现优先级为手动目录 → 环境变量 → 用户默认目录；文件变化静默约 5 秒后扫描，每 15 分钟兜底，最近 48 小时增量，每 24 小时全量。扫描由短生命周期 sidecar 执行且有 2 分钟超时，同一时刻只允许一个扫描；`token-queue.json` 保存已确认稳定哈希，重复复扫不会重复上报或计数。托盘“设置”可手动填写 Codex/ZCode/DSH/WorkBuddy 数据根，保存后立即执行一次全量扫描，也可点击“重新扫描 AI Tokens”手动全量校准。WorkBuddy 只监听 `projects`，不会被配置、认证或 SQLite WAL 的频繁变化反复唤醒。
6. **当前真实验收**：2026-08-23 22:45 完成四来源全量扫描：Codex 46 文件、ZCode 1 库、DSH 1 文件、WorkBuddy 4 文件，共解析 4,066 条请求级事件。WorkBuddy 为 12,436,438 Tokens / 166 次请求，独立全量耗时约 1.2 秒；DSH 为 18,861,837 Tokens / 124 次请求。四个来源均为 `ready/data_and_app`，随后增量扫描 WorkBuddy 新文件 0、上传 0，累计未重复。
7. **M2 真实验收**：2026-08-24 00:02:18，本机非管理员进程成功入库 CPU 23.5%、GPU 52%、内存 70.7%、显存 30.2%、GPU 57°C、可用功耗 15.1W；CPU 温度驱动只返回 0°C，已过滤为不可用；当前存储未提供硬盘占用。真实 `/api/hardware/current` 与日趋势均返回分钟数据，软件和 Token 同期继续上传。
8. **下一步扩展**：进入 M3，优先完善 FE-01 实时仪表和 FE-02 星期×小时活跃热力图；硬件侧可后续增加管理员启动引导、传感器来源说明与异常峰值标记。

## 五、如何运行

M1.5 系统由前端、后端、C# 采集器和 Rust Token sidecar 组成（详见 README）：

1. **后端**：使用 Node.js 24。首次在 `server/` 执行 `npm install`，以后直接执行 `npm start`；当前开发机默认终端即为 Node.js 24，无需指定旧版运行时路径。首启自动生成 `server/config.json` 和上报 Token，运行窗口需保持开启。
2. **采集端**：当前开发机直接运行 `collector/SimmerCollector.exe`，同目录保留 `simmer-token-scan.exe`。托盘“设置”中填写服务器地址和 Token；“启用硬件监控”默认开启，部分温度/功耗/主板传感器可能需要以管理员身份启动，但普通权限能读取的指标仍会照常上报。四个 AI 数据目录留空会自动发现；DSH 手动目录通常为 `%USERPROFILE%\.dsh`，WorkBuddy 通常为 `%USERPROFILE%\.workbuddy`。勾选登录自启使用当前用户启动项，无需管理员权限。
3. **面板**：浏览器访问 `http://127.0.0.1:8788/index.html` 或 `http://localhost:8788/index.html`。顶栏显示“● 实时数据”代表真实链路正常；后端未连接时自动回退演示模式。
4. **停止**：后端窗口按 `Ctrl+C`；采集端在系统托盘右键退出。端口 8788 提示被占用通常代表后端已经启动，无需重复运行。
5. **一键启动**：当前开发机可双击仓库根目录 `启动 Jitang Simmer.cmd`；脚本检查终端 PATH 中的 Node.js 24，依次启动后端、采集器并打开面板。
6. **重新构建采集端**：在 PowerShell 执行 `collector/build.ps1`。本机已安装 rustup/cargo/rustc 1.98.0 与 Visual Studio Build Tools 2026 C++ 工作负载，Cargo 目录已加入用户 PATH；脚本构建固定提交的 Rust sidecar、发布 .NET 8 单文件采集器，再复制到 `collector/`。两个运行 EXE 均被 `.gitignore` 忽略，不进入 Git。安装器提示完成一次系统重启以结束注册，但当前会话已经通过独立 `rustc` 编译运行验证。
